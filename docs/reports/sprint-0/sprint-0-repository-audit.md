## 2. Reusable Code From the Existing Three Doors Prototype

Reusable parts:

- Supabase REST request approach.
- `room_code` based room isolation.
- Three player slots: `GAL-A`, `GAL-B`, `GAL-C`.
- Basic private choice submission.
- Basic duplicate prevention through database uniqueness.
- Polling-based refresh.
- Three-player reveal after all roles submit.
- Teacher room watcher.
- Teacher room reset.
- GitHub Pages static hosting path.
- Human-readable network error hints.

Not suitable as final architecture without refactoring:

- Player and teacher logic are each inside one large HTML file.
- Scene content is hard-coded.
- Scene state exists mostly in browser memory.
- No room/session table.
- No secure player session token.
- No robust reconnect.
- No reusable DiscussionRoom.
- No final vote.
- No clue/inventory engine.
- No agent adapter.
- Teacher console displays private choices immediately.
- Public reset uses broad DELETE behavior.

## 5. Gaps Between Current Code and the Three Specifications

Major gaps:

- The specification requires a 17 ACT state machine; current prototype has only two demo scenes.
- The specification separates Game Track and Behavior Track; current schema only stores choices.
- The specification separates first private choice and final group vote; current prototype has no final vote.
- The specification requires reusable DiscussionRoom; current prototype has no discussion feature.
- The specification requires player session identity and reconnect; current prototype uses manual role selection.
- The specification requires teacher console to hide private choice content before reveal; current teacher page shows choices directly.
- The specification requires event logging; current prototype only logs choices.
- The specification requires agent adapter and schema validation; current prototype has no agent boundary.
- The specification requires prediction lock; current prototype has no prediction system.
- The specification requires Asset Manager; current prototype has no asset manager or manifest.
- The specification requires database migrations; current repository has no `/database`.
- The specification requires modular code; current implementation is two single-file HTML pages.
- The specification requires architecture/testing docs and changelog; these are not yet present.

Summary:

The existing prototype proves the technical route works:

```text
GitHub Pages -> browser clients -> Supabase REST
```

It should be treated as a validated prototype, not as the final implementation structure.

## 7. Database Migration Plan

Recommended migration order:

```text
001_core.sql
002_discussion.sql
003_behavior_events.sql
004_assets.sql
005_predictions.sql
```

### 001_core.sql

Tables:

- `rooms`
- `players`
- `player_sessions`
- `room_state`
- `player_decisions`
- `game_events`

Important constraints:

```text
unique(room_code, scene_id, player_id, decision_type)
```

Purpose:

- Room lifecycle.
- Player identity.
- Reconnect token.
- Current scene/phase.
- Private first choice lock.
- Core event log.

### 002_discussion.sql

Tables:

- `discussion_sessions`
- `dialogue_messages`
- `final_votes`

Purpose:

- Reusable DiscussionRoom.
- Dialogue transcript.
- Final group decision separated from first private choice.

### 003_behavior_events.sql

Tables:

- `behavior_events`
- `observable_features`

Purpose:

- Store raw behavior-relevant events.
- Store observable features without creating new top-level behavior patterns.

### 004_assets.sql

Tables:

- `asset_manifest`
- `asset_submissions`
- `asset_reviews`

Purpose:

- Asset Manager.
- Placeholder-first workflow.
- Upload/review/active asset lifecycle.

### 005_predictions.sql

Tables:

- `agent_runs`
- `behavior_reports`
- `predictions`
- `prediction_results`

Purpose:

- Agent analysis.
- Structured reports.
- Prediction locking.
- Later comparison between prediction and student action.

Security requirements:

- Browser uses publishable key only.
- No service-role key in repository.
- RLS must be explicit.
- Test-only wide policies must be clearly marked.
- Public DELETE/reset should not remain unrestricted in production-like use.
