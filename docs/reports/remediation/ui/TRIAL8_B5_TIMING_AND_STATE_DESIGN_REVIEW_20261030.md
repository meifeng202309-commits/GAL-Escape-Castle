## Critical review of State Recorder & Reporter + State Synchronizer

The proposed comparator must be against the **last server-acknowledged** player-originated version, keyed by room/player/session/round and command identity. Comparing to the last locally sent snapshot risks dropping a write when a response is lost. Yet a single latest-state row cannot replace an append-only event/command record: two chat messages between 2 s checks collapse to one; a vote change/retry can overwrite the first accepted vote; an offline stale upload can overwrite a later online action; Teacher Open Vote and three-player consensus are server-only transitions; a role switch must not leak prior private clues; inventory/Pocket history cannot be reconstructed from one shallow snapshot. Heartbeat confirms authenticated communication, not that the tab is being viewed, and must never move a game phase.

Illustrative **one-minute arithmetic**, not production usage: three Players, a 2 s check example, 20 s heartbeat example, a 1.4 s effective frame period (1.2 s scheduled poll plus illustrative 0.2 s frame), and eight read RPCs per active frame. `tests/trial8-b5-design-cost-model.mjs` computes 42 frames/player/minute, ~1008 read RPCs/minute with current fanout, and ~126 RPCs/minute if a consolidated projection replaces eight network calls. Actual server read work may remain similar or grow inside one function. A full-state upload every 2 s adds **90 writes/minute idle**. Change-only upload adds **zero idle state writes** but up to **9 heartbeat writes/minute** if no other successful communication qualifies; with regular successful authenticated reads, heartbeat could be zero. Current event RPCs already add **zero idle mutation writes**. In an illustrative 10 actions/player/minute, existing event RPCs are 30 writes/minute; change-only reporting needs up to 30 individually preserved action writes, while 2 s full-state uploads remain 90 and can lose intermediate actions. These assumptions are examples, not observed traffic. Serialization/comparison is O(number of meaningful fields) per check, plus version, outbox and conflict handling; it is not free even when uploads are suppressed.

| Option | Network/read effect | Required authority/history | Migration and failure cost |
|---|---|---|---|
| A. Full state uploads | Adds periodic writes; read fanout unchanged unless separately rebuilt | Needs event history and server validation anyway | Largest schema/RPC/client rewrite; stale overwrite and privacy risk. |
| B. Change-only + heartbeat | Avoids redundant uploads; read fanout and queued poll unchanged | Still needs idempotent commands, immutable chat/vote history, server consensus/Teacher gate | Comparator, acknowledged version, outbox, heartbeat/presence, conflict and reconnect migrations; little benefit over existing action-triggered mutation RPCs. |
| C. Keep mutation RPCs, consolidate authorized Player reads | Can cut browser request count and serial network stages if server projection is efficient | Existing event history, idempotency and server authority remain | Smallest conceptual migration, but one large projection can be slow, fail atomically, or expose private fields if role filtering is wrong; needs measured DB workload and privacy tests. |

**Recommendation:** reject A and B as latency remediation at present. B solves redundant uploads that the current action-triggered design largely avoids; neither addresses the confirmed *read* fanout or T2's missing outgoing Player requests. Prioritize C only as an isolated experiment after confirming the Player request-gap cause and measuring server query cost. A narrower phase-specific read can be tested first for ACT9/10, but it must preserve S8 lifecycle authority, session epoch/generation guards, Teacher gates, command idempotency, private role projection, and full-frame convergence.

Proposed isolated A/B/C comparison in the existing harness: replay the same ACT1–13 action fixture and a four-page Teacher/three-Player barrier with deterministic zero human think-time. A and B remain test-only mock reporters with an append-only event ledger alongside their latest-state row; C retains existing mutation RPCs and returns a single role-filtered projection. Capture per-role request rate/bytes, mocked write count, simulated DB reads, click→server transition→DOM, stale/offline retry, two messages inside one check, role-switch privacy and three simultaneous votes. Repeat at 0/100/250/1000 ms and stalled/failed reads, keeping the same seeds and payload histories. Compare the cost model against actual Supabase query plans and a supervised disposable-room browser trace before any source or schema authorization. None of these alternatives has been implemented in product code.
