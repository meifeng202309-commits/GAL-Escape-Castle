Date: 2026-10-30. Scope: CA 18:30 root-cause-first instruction. Read-only T2 database/event evidence from the prior ACT1–ACT13 matrix was cross-checked against Supabase historical `edge_logs` for 2026-10-29 15:20–15:40 UTC. Logs expose RPC path, response status, gateway timestamp, and `response.origin_time`; they do **not** expose each player's browser click, network round trip, response body, DOM visibility, focus, or tab lifecycle. Shared RPC counts cannot identify individual tabs. The isolated experiment below is a scheduler model, not product code or a production measurement.

## Client mechanism and bounded experiment

Current `loadPlayerFrame` performs `s8_get_player_state` then `s2_get_player_state` serially, waits for five parallel projections via `Promise.allSettled`, then waits for conditional S5 discussion/S6 wait projections. A mutation calls `refreshState`; if a poll frame is in flight, its refresh is queued and the older frame must settle first. Generation checks discard stale results. Polling schedules the next 1200 ms only after the complete frame. A hung request has no explicit timeout in this coordinator. A failed projection aborts the full frame and leaves unverified controls disabled until a later confirmed frame. Teacher `loadState` uses a 1200 ms `setInterval` without in-flight serialization, so concurrent Teacher reads are possible; T2 aggregate traffic does not prove one Teacher tab overlapped.

B2/B3 real-client mocked browser fixtures show that injecting 250 ms into each read makes full-frame follow-up reads dominate local click→visible times (~0.8–1.1 s). The DOM render portion was generally single-digit milliseconds, with some tens-of-ms local variation; this falsifies a claim that synchronous DOM rendering alone explains those injected-delay samples. The fixtures also show an existing B3 Waiting indicator in 28–70 ms, but that indicator does not improve authoritative visibility.

`tests/trial8-target-projection-isolation.mjs` is a **model only** of a possible narrow confirmed-target read after both authority reads. With authority/target/unrelated delays of 10/10/150 ms, full-frame visibility took 202 ms and target visibility 82 ms; at 50/50/250 ms, 353 vs 183 ms. Equal 10/10/10 ms delays gave 56 vs 65 ms (no gain). A 200 ms predecessor remained in the candidate's critical path (384 vs 250 ms); stale generation was discarded. This falsifies the claim that target projection alone cures preceding queued frames or missing requests. The model cannot establish safety of a partial production commit; cross-projection consistency and identity validation would need a real-client test before source changes.

## Ranked causal diagnosis

1. **Confirmed gates and human interval accounting:** Teacher Open Vote and three-player barriers account for some large waits. Server transitions seen in T2 were prompt. Preserve these semantics.
2. **Observed Player request generation/delivery gap:** 15:31–15:32 sparse Player RPC traffic coincides with continued Teacher RPCs and repeated chat 400s. This is the strongest production lead for a genuine stuck experience, but the cause is unknown. A browser performance/network trace and response bodies from a supervised reproduction are required to distinguish suspension, network, coordinator starvation, and stale retries.
3. **Confirmed full-frame amplification under injected delay:** serial authority reads, broad fanout and queued predecessor can add hundreds of milliseconds to seconds in controlled browser tests. Production origin-time tails make this plausible as an intermittent contributor, not proof of a minute-scale T2 cause.
4. **Error and retry path:** fourteen chat 400s over 15:31–15:32 suggest rejected actions could prolong perceived progress. Error type and retry origin remain unmeasured.
5. **DOM/asset scheduling:** local mutation-to-visible DOM work was small for the tested interaction families. Asset decode and browser background throttling remain unmeasured in T2; neither should be asserted as root cause.

## Next falsifying gate and proposed fix

Before product-source optimization, run a supervised browser trace for one Player and Teacher covering ACT2 vote/chat, ACT9 door, ACT10 private/vote/Continue, ACT11 allocation, and representative ACT1/3/4/5/6/7/8/12/13 actions. Record click, mutation request/response, every projection start/end/status, refresh queue/generation/commit, `visibilitychange`/focus, DOM target visibility, request error body category, and Teacher operation/participant barrier timestamps. Use disposable test room only under separate authorization. If no Player requests occur while visible and online, inspect polling scheduler and refresh promise/timeout path; if requests continue but DOM stalls, inspect frame commit and render. Reproduce with parallel Teacher operations and a stalled projection to test queue starvation. This gate can falsify each leading hypothesis.

The **minimal experimental source candidate**, subject to CA permission, is a phase-specific confirmed-target projection path for ACT9/10 after the existing authority and session/generation checks, leaving full-frame polling and Teacher gates intact. Test it first in an isolated real-client fixture against 0/250/1000 ms irrelevant-projection delays, a stalled queued predecessor, stale generation, rejection/retry, and concurrent Teacher operation. Accept only if click→**authoritative** target visibility falls while no stale or premature Scene/vote state appears. The model demonstrates potential only where unrelated projections dominate; it cannot repair a 2-minute request gap. Do not ship B3 or the pressed-button module as a latency fix.
