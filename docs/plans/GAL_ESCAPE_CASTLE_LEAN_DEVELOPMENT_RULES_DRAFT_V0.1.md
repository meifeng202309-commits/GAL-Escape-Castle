# GAL Escape Castle — 提高开发效率、简化繁复流程规则（讨论草案 V0.1）

Date: 2026-11-23
Proposed by: Teacher / drafted by CA
Status: **DISCUSSION DRAFT — NOT ACTIVE; pending CD and GA critical review and Teacher final approval**
Scope: GAL Escape Castle 剩余开发、Debug、素材和文案整合、教学试玩、CA 审核与交接。
Basis: Teacher 2026-11-23 指示；现行 `docs/plans/DEBUG_V4_TRIAL_FIRST_AUDIT_PROCESS_V1.0.md` (2026-10-21)；CA-338–344 实际交付瓶颈。
Precedence: 草案不替代现行权限/安全边界；经 Teacher 批准后再明确与旧流程的优先级关系。

## 1. 唯一开发目标与风险背景

本游戏**只为教学使用**，不是公开商业产品；**同一局最多四位使用者：一位 Teacher + 三位 GAL Players（Gitte / Anna / Linda）**；以匿名游戏身份使用，不收集真实个人隐私资料。教学使用场景下**没有需要额外设计的个人隐私泄露风险**，也无须以大规模公众服务的负载、监管合规、商业可用性标准进行工程化。

实际目标：**以最少开发与管理成本，尽快让 Teacher + 三位玩家能完整玩通 ACT1–ACT14，正确看到获批的中荷文案、图片、按钮和投票结果，并能在失败时重新加入或开启下一局。** 玩家实际可见和可玩，比内部流程完备优先。

注：不因「匿名」取消已有三位玩家的角色私有线索隔离；这是游戏公平和剧情机制，不是额外个人隐私防护项目。仍须避免误删历史数据和无授权生产写入。游戏已在互联网上通过 Pages 可访问，不得声称物理上与互联网隔绝；只是**预期使用者范围严格限定为课堂四人**。

## 2. 总规则：必要性检验与停工条件

所有 Agent（CD、CA、GA、VA、ISA 等）在开始任何新工作前只做一个判断：
**「不做它，会不会实际妨碍四人教学试玩、已批准内容的正确呈现、必要的恢复，或者明确要求的生产授权？」**

- **不会：默认不做**。不得自行把 P2/边缘问题、安全强化、性能微优化、可观测性、兼容性穷举、文档完善、历史字段治理、架构美化加入关键路径。
- **会：选用最小现有手段**，优先复用源码、素材键、现有测试和现有回退点；不另造 framework、通用抽象、后台服务、数据表或 workflow。
- **证据不足：标记待观察，不得因为「还没有证明绝对安全」就阻断试玩**。由 Teacher 实测决定优先级。
- 唯一必要 STOP：真实可复现的 P0（不能 join/start/advance、无法恢复、错误剧情推进或角色线索跨人可见）；严重数据损坏风险；明确缺失的受保护资源/生产写入权限；回退路径不可用。其余小毛病留入 backlog，不自动展开调查链。

## 3. 编码风格：修 Bug，而非重建系统

1. **Smallest Correct Change**：每项问题优先直接修改现有 handler、状态映射、文本调用或图片引用。能改 5–20 行就不新增模块；若必须新增模块/数据库迁移，CD 用 2–3 句话证明现有实现为何做不到。
2. **不为推测风险写防御代码**：只处理已发生、可复现或会阻断主要路径的错误。不加入无证据的备用状态机、复杂兼容层、统一治理平台、通用恢复 framework。
3. **素材直连**：VA 已批准的图片不再交 CD 做像素、排版或叠字加工；复用已经存在的资源管理机制，不为每张图创造独立发布设计。确需 Asset Manager 注册/激活时，合并一次处理。
4. **Runtime 文案是用户可见的交付物**：GA 只负责确实需要的 canonical CN/NL 文案语义和键映射，CD 只负责在正确剧情状态展示；不重新争论已获 Teacher 批准的句子。遇到少量 ambiguous 分支列出具体键/页，不把整个工作包冻结。
5. **不要改动未涉及的功能**；代码已正常的投票、画面、教学逻辑不因新清理任务而重构。

## 4. 任务分组：一次完成有意义的功能包

- 以**Teacher 试跑报告**为需求清单，一次任务包涵盖同一轮已确认的相关修复；按最短 playable route 排序：P0 进不去/过不去 → 已批准文案与图片完整呈现 → P1 小体验问题 → P2 后置。
- CD 对一个有明确需求的工作包连续完成「代码改动 → 必要本地验证 → 可供 CA 一次审查的整体成果」，中途**不为例行检查**再发信申请下一小步。
- 对真正由 GA/VA 掌握的文案/原图，CD 提供**精确待办清单**并继续完成不受阻的任务。GA/VA 只处理明确缺项，不增加设计讨论或美术迭代。
- **不得用单个内部模块 PASS 宣称 Teacher 问题已解决**。例如「ACT9 asset test PASS」不等于「整批图片已上线」，「3 个 localization keys 更新」不等于「三角色 Runtime 全量更新」。

## 5. 测试、审计、发布：一轮完成，按实际风险决定深度

**默认最低测试**：
- 语法/静态检查（复用已有命令）；
- 主要成功路径 1 次；
- 与 bug 最相关的失败/回退路径 1 次；
- 改过的 Scene/Runtime/Action 在真实浏览器中肉眼可见（截图或最小三角色模拟）。
- 现成自动 CI 可以继续运行，但无需为每个 PASS 产生独立审计信。

**禁止默认新增**：每个小 Bug 独立 Playwright suite、独立 SQL 生命周期演练、从 migration 001 重跑全部历史、全表全字段 snapshot/hash 对比、多阶段审计报告、独立 Recovery 设计文档、跨工具多重证明链。只有 CD 指明现有测试确实覆盖不了的**具体重大失败模式**，CA 才可要求针对性增加，优先补在现有测试内。

**CA 一次集中审核**：核对 Teacher 需求列表、改动 diff、必要测试结果和关键 P0 回归；若未发现真实阻断，直接 PASS；最多提出三个明确高影响 blocker。低影响不写往返信，登记 backlog。杜绝「源码 PASS → 测试 PASS → 独立演练 PASS → 发布准备 PASS」的多轮移交链。

**发布原则**：对已经批准的功能/图片/文案按逻辑组成一次最小可玩的发布批次。保留当前可恢复的前一版本，做最短 Teacher + 三 Player smoke，确认输入、投票、场景切换及文字显示。**不自动要求生产级全链路认证**。既有自动工具可低成本运行则保留，但不形成新的阻断任务。

**权限保底（不能由本草案取消）**：生产数据库变更、Storage 资产发布/激活、GitHub Pages 上线等需要遵守当前有效的明确授权和平台工具权限；不能复用已失效的一次性授权。若生产状态存在真实漂移，采取最小必要检查和恢复。保留历史游戏数据，分局用 `run_id` 区分；不擅自删除数据。技术性不可恢复风险需 STOP。**规则简化不等于允许无授权发布**。

## 6. 文档和通信：减少到真正有用

- 默认一个开发包只需要**一份 CA→CD 工作授权/需求信、一份 CD→CA 结果信、一次 CA 结论**，以及现有 Action Log 的简明条目。需要 Teacher/GA/VA 决策时，只发给确实负责的人；不广播 FYI。
- CD 结果信原则上不超过一屏：**修了什么、未修什么、验证结果、剩余阻塞、部署状态和 NEXT_OWNER**；可附源代码 commit/CI 链接，避免重复粘贴证明文本。
- 取消低风险任务的多份提案、独立设计意见、反复封存 SHA、重复做完整历史梳理；既有文件能表达的不要再复制新文档。
- 依照现行 Action Log 和 Agent 责任边界保留**必要的简短 ownership 交接**；不新增审批层级。

## 7. 立即适用的目标（在 Teacher 批准本草案后）

现有 CA-338 作为**唯一主工作包**：
1. CD 已修的完成局重播、Join/换局问题及未上线源码，和已获批图片更新，纳入一个可玩的测试候选。
2. GA 完成「三名玩家 216 个页面条目」的批准中荷 Runtime 显示映射，CD 集成；不把 216 行机械当作 216 个独立新 key。
3. VA 仅解决 Linda 怀表背面 approved image/sidecar 字节不一致，不重新设计；CD 不得加工像素。
4. CD 整体验收 Scene/Runtime/Action 正确展示，CA 一次审计后提请必要生产授权，并组织最小四人试玩；无关 backlog 继续挂起。
5. 若 GA/VA 个别事项无法及时解决，明确列出**玩家可见的具体缺项和绕行方式**，由 Teacher 决定是否允许一个有意识的不完整试玩版本；不因一两个非 P0 缺项无限等待。

## 8. 可衡量的效率指标

记录三个数字，不创建新 Dashboard：
- 每份 Teacher 报告从提交到**真实玩家可见修复**的天数；
- 每个开发包的 CA↔CD **交接轮数**（目标一次修复＋一次审计）；
- 每轮上线实际解决的 Teacher 问题数量，以及还留多少未解决项。

目标不是增加提交/日志数量，而是加快 Teacher 能实际进入游戏、看到正确画面并完成全流程的速度。
