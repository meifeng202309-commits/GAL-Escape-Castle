## 三、对 CA 原 Round III 的具体修正

### 修正 1（已确定）：ACT2 FOLLOW SIGN

**旧提案中容易增加工程成本的表述：**  
将“屏幕上看到提示牌”“玩家实际确认看到提示牌”“正在改变目的地前往 Library”拆成需要分别记录的状态，并可能考虑增加确认按钮。

**教师现在确定的简单方案：**
1. 继续复用现有 Player 按钮 **FOLLOW SIGN**；不额外增加“我看到了提示牌”按钮。
2. 玩家点击该按钮，**现有服务器操作直接**把其位置设为 `library`。
3. Teacher UI 根据该服务器已确认的位置变化显示 **“Anna 进入图书馆”** 等同类文字；最终显示用词与现有程序统一。
4. 按钮点击之前，Teacher 仍仅展示主程序当前实际确认的位置/目的地；**不**显示尚未记录的“已经看到牌子”或“正在改道”。
5. Observer 读取并忠实显示服务器已发布的状态，不自行推断、不创设多余 intermediate phase。

**节省成本：** 不必增加单独的 sign-acknowledged 状态、迁移列、第二按钮或额外状态转换/测试路径。此处以现有 `s3b_follow_sign` 的真实行为为合同候选，最终应由 CD 验证现行函数及 Teacher S7 的可读输出。

### 修正 2（记录审查，不提前接受）：通用 TOP

保留教师已确认的 **Option B**（使用经授权的 Teacher Override 恢复结果，而不往普通投票表添加虚拟玩家票）及按 ACT 开头恢复、必要资源/记忆补齐、真实记录与恢复结果严格区分的目标。

但 CD 有实际证据指出现有 Override 仅覆盖 ACT1–5 的限定交互，不能无成本地扩为 13 个通用 TOP。**本轮不调整教师的最终需求，也不接受 CD 的缩减范围作为定案**；只记录技术复杂度及需要与 CD 讨论的具体约束。不得向 CD 立即授权通用 TOP。

### 修正 3（记录审查，不提前接受）：讨论、投票结果、冷却和 Observer

保留教师先前确定的设计原则：
- NORMAL Discussion 由教师按 Open Vote 按钮控制；游戏负责判断投票是否合法及如何处理结果。
- 多数、平票、错误结果向玩家/教师以统一三秒方式显示；显示方式统一并不意味着所有场景使用同一个投票/闯关规则。
- ACT3 的三秒服务器受理冷却必须对跨浏览器同时输入生效。
- 主程序发布权威状态；Observer 不决定游戏逻辑。

CD 报告这几项存在明确的 SQL/读取合同差异，**本轮只登记其发现与估算，不据此决定具体函数级修改方式、时序或批量工作包授权**。

### 修正 4（保留）：教师状态和无记录原因

Teacher 显示当前 interaction 范围内的具体已确认行为，而非空泛的 waiting；网络失败时应保留 `NO_CONFIRMED_SERVER_RECORD` 与“从未尝试”之间的区别。由主程序拥有该事实，Observer 不编造。
