# GAL Escape Castle — Implementation-Path-Based TCA Workflow Rules V1.0 (FINAL)
**Status:** GA PROCESS RULE FINAL — documentary planning and bounded TCA candidate selection only; **NOT** a CD coding release, production architecture approval, or supersession of project ACTIVE protocols.  
**Effective for:** GA implementation-path feasibility research and GA/TCA/CA coordination under the Teacher-approved trial.  
**Governance:** Existing ACTIVE onboarding, Agent Action Log rules, inter-agent communication, V4 approved gameplay/Debug Implementation Plan, canonical owner and CA audit/release gates prevail in any conflict.  
**Provenance:** Teacher approved the workflow drafting and independent consultation. CA method review `CA_to_GA_20261010T165000Z_implementation-path-v10-text-and-bmin-pilot-audit.md` reports `METHOD_TEXT_PASS_FOR_OWNER_FINALIZATION`; TCA review and revised route-binding note on `tca/p01-library-five-slot-draft-20261010` were reconciled. This FINAL is a **GA-owned coordination method**, not independent authorization to constrain future CD architecture.

## 1. Purpose and hard boundary
Start at CD's real frozen source/release boundary and the next approved or expected V4 package. Define verifiable Integration Checkpoints (ICs), investigate materially viable implementation routes, and select only economically justified isolated TCA Blocks. Optimize forward-looking **remaining CD implementation + Pack integration + tests + regressions + maintenance**, not the amount of code TCA writes. No study/report/CA concurrence alone releases CD, TCA coding, SQL, RPC, production deployment, assets or runtime alterations.

## 2. Investigation scope and evidence
Each GA study pins branch, commit, relevant file blob SHA, CD freeze checkpoint, current CA gate and exact V4 acceptance. Study only the minimal direct source/consumer/test neighborhood; widen to effective SQL/overloads/grants and data lineage only as a real dependency requires. Mark individual assertions `VERIFIED_WHAT`, `INFERRED` or `PROPOSED`, and tag source evidence `DECLARED_CANONICAL`, `SOURCE_STATIC`, `TEST_MOCK`, `DEPLOYED_VERIFIED`. A migration file or mocked browser test **does not** verify effective deployed RPC/grants. Unknown facts are `NOT_VERIFIED`, with owner, impact and required confirmation.

## 3. IC contractual maturity
A heading or package boundary is not itself a proven checkpoint. An IC defines proposed entry (input/authority/run/permissions), exit (observable data/behavior/effects), invariants (privacy, ownership, transition, reconnect/idempotency), direct semantic consumer obligation, applicable tests, and STOP/dependency conditions.
Tag IC `PROPOSED`, `SOURCE_VERIFIED`, `ACCEPTED_FOR_PLANNING` or `IMPLEMENTATION_VERIFIED`. These tags express distinct evidence and decisions: `ACCEPTED_FOR_PLANNING` allows route comparison but never proves operational behavior or authorizes production Packs. A future semantic consumer obligation may be approved before its physical function/DOM callsite exists. Call the physical consumer `SOURCE_VERIFIED` only when actually present, otherwise `PROPOSED`. Never invent a payload/adapter or treat a prepared S5 row as activated authority.

## 4. Implementation route feasibility
GA proposes 1–3 real alternatives only where materially distinct; one feasible route and `NO WORTHWHILE TCA PACK` are valid results. Compare correctness/authority, genuine consumer, contract fit, source changes, integration effort, testability, maintenance/bloat, reversibility and expected net remaining cost. Document one falsification case and best surviving alternative. STOP speculative comparison if producer/consumer uncertainty prevents meaningful ranking or study plus probable integration costs plausibly exceed CD effort saved. No global A–F speculative master blueprint, invented labor-hour precision or arbitrary two-Pack quota.

## 5. Route approval and binding properties
Every route carries exactly one status: `PROPOSED`, `RECOMMENDED_ADVISORY`, or `APPROVED_ROUTE_DEFAULT_BINDING`. A route becomes `APPROVED_ROUTE_DEFAULT_BINDING` **only** when an *existing, explicitly authorized* technical/canonical owner or gate approves its particular route-defining properties after alternatives review and CA independent examination. Approval record MUST specify owner, decision reference, governing scope, exactly binding route properties, assumptions, reopening triggers and falsifying test or surviving alternative. GA preference, CA signoff alone, multiple-model agreement or TCA Pack existence NEVER automatically upgrades route authority.

Independently, existing canonical IC semantics, data/authority constraints, invariants, release sequencing and acceptance are binding within their established owner authority. Unless an owner formally approves route architecture, algorithms, module/RPC count, implementation mechanics and helper names remain advisory.

## 6. Future CD implementation freedom, deviation and cost
On legitimately authorized resume CD reads the fresh source/gate/approved ICs and any expressly bound route, then independently chooses whether to `INTEGRATE`, `ADAPT` or `DISCARD` each TCA Pack. A truly approved route is the default; **material** change to its named bound data flow, state ownership, RPC/interface set, synchronization or dependency architecture requires new concrete evidence of incompatibility/unsafe behavior or substantive forward-looking cost/risk/reliability benefit, with independent CA review under the **existing** gate and canonical-owner decision if required. Purely `RECOMMENDED_ADVISORY` choices do not create extra vetoes. Equivalent within-route internal algorithms/helper organization/naming need no extra approval. An urgent safety/privacy/authority flaw stops only the affected work and triggers normal escalation. Sunk GA/CA/TCA effort is not a rationale to perpetuate inferior remaining-cost work.

## 7. TCA production-Block selection
GA Pass 1 requires approved unmet acceptance or evidenced meaningful consolidation, real existing consumer or owner-approved frozen narrow adapter seam, pinned source/interface and bounded authority, net integration benefit, testable independent discard boundary. Ask before code: **if the Pack is removed, which approved acceptance test fails or demonstrated duplicate/maintenance burden returns?** A future proposed RPC or imagined physical consumer is inadequate. Route-independent helpers are preferred only if >=2 actually feasible routes demonstrate the same source-grounded observable input/output contract AND proposed integration diff genuinely consumes its output; otherwise use a small route-specific Block with positive net value, or no Pack.
Do not add unnecessary production modules, state mirrors, new APIs, generalized frameworks or duplicate validated functionality merely to keep TCA busy.

## 8. Review stages and test evidence
- **GA Pass 1:** WHY/WHAT, acceptance/consumer, route/IC proposal, technical breadth, cost/necessity and S/R/X.
- **TCA Pass 2 (before any coding):** independently check pinned target and direct consumer/callers, actual existing helpers and tests, reuse lineage `REUSED_NOW`/`ADAPTED_COPY`/`CONSIDERED_NOT_USED`/`PLANNED_NOT_INTEGRATED`, deletion-falsification and bounded integration. STOP affected Pack for nonexistent consumer/value, protected authority crossing, material mismatch or self-expanded scope; WARN/target recheck benign source drift/soft code footprint.
- **CA Pass 3:** independently falsify GA/TCA claims and verify `TECHNICAL_INTEGRITY` and `PRODUCTION_VALUE` separately. BOTH PASS for `STATIC_READY`, which is *not* production integration.
Four evidence tiers `PACK_UNIT`, `PATCH_STATIC`, `CALLSITE_INTEGRATED`, `BROWSER_SERVER`, each with executor and PASS/FAIL/NOT_RUN, never conflated. Actual integration and authorized runtime verification belong to future CD; CA audits under normal gates. No extra routine committee or pre-code approval chain.

One compact IC/route study is sufficient; embed existing-source lineage, options, unknown owner dependencies, falsifiers, approximate economics, proposed small Blocks and `NO PACK` outcome. GA requests independent CA technical challenge and TCA practitioner integration challenge when substantive; merge material corrections before recording method acceptance. Authorized production deviations and CD release use the current project governance, not this document. On CD resume, the latest approved implementation-boundary record and TBF register should be consulted **only after valid CD release**.
