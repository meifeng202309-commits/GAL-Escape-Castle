# 从创意到游戏成品的研发流程 V1.0

## 1. 文档目的

本流程用于描述一个教育型互动游戏从最初需求，到创意、原型、技术验证、正式开发、测试与发布的完整过程。

它不是传统“先写完整需求，再一次性开发”的瀑布流程。

更适合本项目的方法是：

> **需求 → 创意 → 探索性原型 → 暴露难点 → 解决难点 → 细化 → 测试 → 再细化 → 发布**

其核心是多轮循环。

**强制质量规则：从本版本起，今后的 Agent / Codex 每完成一个新的“可交付版本”——无论是故事设计、游戏脚本、代码、Agent 规则、数据库结构还是 UI 流程——都必须先执行一次多视角 Devil Check（挑剔审查），修复发现的问题后，才能把该版本标记为完成。**

Devil Check 不是发布前才做的一次检查，而是每一轮迭代的质量门（quality gate）。

---

# 2. 总流程

```text
教育需求
   ↓
明确要观察/训练的能力
   ↓
形成游戏创意
   ↓
探索性剧本 / Prototype
   ↓
找出主要难点
   ├─ 剧情逻辑
   ├─ 多人互动
   ├─ 技术实现
   ├─ 数据记录
   ├─ AI分析
   └─ 教学有效性
   ↓
逐项解决难点
   ↓
技术最小实验
   ↓
细化游戏脚本
   ↓
多视角 Devil Check（脚本版）
   ↓
Codex实现
   ↓
多视角 Devil Check（代码/系统版）
   ↓
三人真实测试
   ↓
发现新问题
   ↓
修改脚本 / 程序 / Agent规则
   ↓
重复测试
   ↓
稳定版本
   ↓
发布
```

# 3. Stage 1：说明教育需求

首先不要从“我要做一个游戏”开始，而从：

> **学生要通过这个活动学到什么？**

开始。

本项目的 Skill 3 原始需求是：

- 让学生理解 AI 可以根据过去行为推断未来行为；
- 但 AI 的预测不是确定事实；
- 学生需要亲自看到“行为数据 → 模式 → 预测”的过程。

原始六类行为模式：

1. Planning vs spontaneity
2. Group role
3. Novelty vs familiarity
4. Social initiative
5. Handling disagreement
6. Reaction under pressure

### 本阶段输出

《教育目标 / 行为指标清单》

---

# 4. Stage 2：形成核心创意

问题：

> 怎样让行为数据自然出现，而不是让学生做一份心理问卷？

核心创意形成：

> 把行为测试藏进一个三人合作冒险游戏。

进一步确定：

> 古堡逃脱

原因：

- 自然包含未知环境；
- 适合路线选择；
- 适合谜题；
- 适合团队合作；
- 适合意见分歧；
- 适合时间压力；
- 容易营造氛围感。

### 本阶段输出

一句话 concept：

> 三名 GAL 在午夜前合作逃出古堡；她们以为自己在解谜，系统同时收集她们的行为轨迹。

---

# 5. Stage 3：探索性剧本

第一版不追求可直接编程。

目的只是回答：

> 这个创意能不能成立？

因此允许：

- 某些分支没有完整收束；
- 技术细节缺失；
- Agent 分析方法没有定义；
- 页面结构没有确定。

本项目输出：

《古堡逃脱游戏脚本 V0.1》

V0.1 的价值：

- 证明故事有吸引力；
- 证明六类 behavior pattern 可以嵌入；
- 证明三人合作比单人版本更适合；
- 暴露真正困难之处。

---

# 6. Stage 4：主动寻找“致命难点”

原型之后不要马上写正式程序。

先问：

> 什么会让这个游戏根本无法运行？

本项目发现的主要难点包括：

### 6.1 Branching Explosion

12 个互动点 × 每点 4 个选择，如果都永久分支，会爆炸。

解决：

> Branch → Local Consequence → Fold Back

即：
- 局部分支
- 不同反馈
- 少量延迟后果
- 主线重新汇合

---

### 6.2 插图工作量

若每个分支都生成图片，成本过高。

解决：

> Scene-based illustration

只为主场景制作约 8–10 张图。

---

### 6.3 三人异地互动

单人故事结构不能直接用于三名学生。

解决：

> Shared story + individual decisions + group decisions

并引入：

- private choice
- reveal
- discussion
- asymmetric information
- timed cooperation

---

### 6.4 异地网络

教师和学生不在同一地点，本地局域网服务器不可用。

解决：

> Supabase Free + GitHub Pages

Supabase：
- 同步状态
- 保存数据

GitHub Pages：
- 发布网页

---

### 6.5 自由讨论如何分析

仅保存聊天文本还不够。

必须定义：

- 数据结构
- Agent 任务
- 行为指标
- evidence
- confidence

---

# 7. Stage 5：做最小技术实验

重要原则：

> 不要拿完整游戏测试新技术。

先做极简版本。

本项目的实验：

## Three Doors

Scene 1：
三人秘密选择 Red / Blue / Black。

系统：
- 等待三人
- reveal
- 自动切换场景

Scene 2：
Run / Hide / Call others。

同时：
- Supabase 保存数据
- 不同浏览器连接
- GitHub Pages 发布

### 技术实验的意义

它验证的不是游戏好不好玩。

它只验证：

- 能否联网
- 能否同步
- 能否记录
- 能否切换场景

---

# 8. Stage 6：技术实验必须记录错误

本项目实际发现：

### 错误 1
最初 Supabase URL 配置错误。

表现：

> Failed to fetch / 网页无法找到数据库。

### 错误 2
本地 file:// 运行增加额外调试变量。

### 解决

改为：

> Supabase → GitHub repository → GitHub Pages webgame

### 原则

每次技术错误都应记录：

- symptom
- root cause
- fix
- prevention

避免正式游戏重复发生。

---

# 9. Stage 7：回到剧本做逻辑审查

技术通路验证后，不能直接开发完整游戏。

需要重新审查探索性剧本。

审查问题：

### A. 因果是否完整？

例如：

> 玩家选择 Great Hall，为什么最后去了 Library？

必须有剧情解释。

---

### B. 玩家失败怎么办？

例如：

> 密码连续输错三次怎么办？

需要 hint / fallback。

---

### C. 自由互动如何实现？

例如：

> “三人讨论”不是需求规格。

必须进一步写：

- 页面
- 聊天
- 时间
- final vote
- 数据记录
- 异常情况

---

### D. AI 到底分析什么？

不能写：

> AI 判断谁是 leader。

必须写：

- 输入是什么
- 输出是什么
- 什么算证据
- 什么不允许推断
- confidence 如何表达

---

# 10. Stage 8：把问题分类

发现问题后，先判断是哪一类。

## Type A：剧情缺口

例：
“无论选哪里都到图书馆。”

解决：
补剧情。

---

## Type B：规则缺口

例：
Red Door 谜题知道逻辑，但没有“怎么触发门”的规则。

解决：
补游戏规则。

---

## Type C：程序需求缺口

例：
三人自由讨论。

解决：
写 Codex requirement。

---

## Type D：Agent 分析缺口

例：
怎样判断“谁寻找证据”。

解决：
定义 analyzer schema。

---

## Type E：实验有效性缺口

例：
AI 在学生回答后再生成预测。

解决：
prediction lock。

---

## Type F：稳定性缺口

例：
刷新页面后丢失进度。

解决：
状态持久化 + reconnect。

---

# 10. Stage 9：版本级 Devil Check（强制质量门）

## 10.1 为什么必须每个版本都做

“脚本读起来顺”不等于“玩家真的能玩”。

“代码能运行”也不等于“多人状态、故事因果、行为分析和教学目标彼此兼容”。

因此每完成一个新的版本，都必须先假设：

> **这个版本里一定还藏着问题。**

Agent 的任务不是证明自己的设计正确，而是尽可能找出：

- 前后设定矛盾；
- 玩家无法理解的步骤；
- 玩家知道了本不该知道的信息；
- 关键线索只存在于某个可选分支；
- 某条路线进入死路；
- 技术状态与故事状态不一致；
- 多人同时操作时无法执行；
- 断线/刷新后无法恢复；
- Agent 分析超出已有证据；
- 教育目标被积分、谜题或剧情机制污染。

Devil Check 的基本态度是：

> **像一个最挑剔的玩家、编剧、程序测试员和研究方法审稿人那样找问题，而不是替设计辩护。**

---

## 10.2 每个新版本必须从不同视角“完整走一遍”

至少包含以下视角。

### Viewpoint A：每一名玩家

分别站在每一名玩家的位置，从头到尾走一次。

本项目中就是：

- Gitte
- Anna
- Linda

每次只允许知道该角色当时实际拥有的信息。

检查：

- 她此刻知道什么？
- 她为什么会看到这个选项？
- 她是否知道下一步要做什么？
- 她是否被要求使用一个自己从未获得的线索？
- 她的选择是否真的会产生可理解的后果？
- 如果她没有在前面选择某个调查动作，后面还能否继续？
- 她是否会因为等待其他玩家而失去方向？

这是 **Player Knowledge / Information-State Check**。

### Viewpoint B：团队整体

把三名玩家作为一个合作团队检查。

检查：

- 是否有真正需要交流的信息差？
- 三个人是否可能互相等待而无人行动？
- 是否存在“两个人都以为第三个人会做”的责任空洞？
- private choice 是否可能提前泄露？
- final decision 是否会错误覆盖 first choice？
- 分歧时有没有明确的收束机制？
- 全员同意时是否还被强迫讨论？
- 没有分歧时，系统是否错误生成 Handling disagreement 数据？

这是 **Multiplayer Interaction Check**。

### Viewpoint C：Game Master / 教师

站在教师端检查：

- 能否判断谁卡住了？
- 能否知道当前 scene / phase？
- 玩家断线时能否恢复？
- Teacher intervention 会不会污染行为数据？
- 私密选择在 Reveal 前是否应该对教师隐藏？
- 是否存在必须人工救场却没有 Teacher Console 功能的情形？

这是 **Operational / Classroom Check**。

### Viewpoint D：Story World / 编剧

不站在任何玩家视角，而站在“故事世界本身”。

检查：

- 时间线是否一致？
- 场景地理是否一致？
- 角色/物品是否突然出现或消失？
- 前面说 Tower 被封，后面是否又无解释地正常开放？
- 某个钥匙、符号、人物、危险是否有 setup？
- 后面重要 payoff 是否有前面铺垫？
- 世界规则是否中途改变？

这是 **Continuity Check（连续性审查）**。

### Viewpoint E：系统 / 服务器

把故事翻译成状态机。

检查：

- 每个 scene 的进入条件是什么？
- 每个 phase 的退出条件是什么？
- 等待三人提交时会发生什么？
- 2/3 已提交时怎样显示？
- duplicate submission 怎么处理？
- reconnect 怎么恢复？
- timeout 时系统走哪条路径？
- Agent API 失败时剧情是否还能继续？
- Supabase URL / key / schema 配置错误时是否有明确提示？

这是 **State-Machine / Failure-Path Check**。

### Viewpoint F：Behavior Analyst

只看数据，不看作者意图。

检查：

- 当前数据真的支持这个 behavior pattern 吗？
- 是否把谜题能力误当成行为模式？
- 是否因为“选对”就认为行为更优？
- 是否从一次选择做稳定人格推断？
- 是否把 observable feature 擅自升级为新 pattern？
- 是否有至少足够的跨场景证据？
- 没有证据时是否允许 `insufficient evidence`？

这是 **Construct Validity Check**。

### Viewpoint G：未来的 Codex / 维护者

假设六个月后由另一个 Agent 接手。

检查：

- 能不能从 README 看懂系统？
- Story 与 Engine 是否分离？
- scene 是否数据驱动？
- 复杂逻辑是否有注释？
- 是否有神秘的 hard-coded 特例？
- 新增一个 scene 是否需要修改大量核心代码？
- 数据 schema 与 Agent schema 是否有文档？
- CHANGELOG 是否说明为什么修改？

这是 **Maintainability Check**。

## 10.3 Devil Check 必须检查的七条“连续性链”

每次版本审查至少逐条检查：

### 1. Information Chain

```text
信息在哪里出现
→ 谁能看到
→ 是否共享
→ 后面谁在使用
```

若后面使用者从未获得该信息，就是逻辑漏洞。

### 2. Object / Prop Chain

```text
道具获得
→ inventory
→ 是否消耗
→ 后续用途
→ 是否仍存在
```

类似电影剧本中的 **prop continuity**。

### 3. Location Chain

```text
当前位置
→ 可走路线
→ travel consequence
→ 下一场景
```

不得瞬移。

### 4. Time Chain

必须区分：

- Real Time
- Story Time

并检查二者不会互相错误覆盖。

### 5. Setup → Payoff Chain

借鉴电影剧本的 **Chekhov's Gun / Setup–Payoff** 方法。

如果后面出现：

- ★钥匙
- 蛇
- 政府通知
- Clock Room
- alarm

就问：

> 前面是否有合理 setup？

反过来：

> 前面强调的东西，后面是否至少产生一次有意义的 payoff？

不是所有细节都必须成为谜题，但重要线索不能成为无意义装饰。

### 6. Choice → Consequence Chain

每个重要选择检查：

```text
choice
→ immediate feedback
→ optional delayed consequence
→ fold-back point
```

玩家至少应感觉到选择留下痕迹。

### 7. Evidence → Inference Chain

```text
raw event
→ observable feature
→ core behavior pattern
→ final wording
```

任何一层不能跳跃。

## 10.4 引入电影剧本常用检查技术

### A. Continuity Breakdown

传统影视制作会逐场检查：

- 时间
- 地点
- 道具
- 服装/状态
- 已知信息
- 前后动作

游戏脚本也应建立一张 Scene Continuity Matrix。

推荐字段：

| Scene | Story Time | Location | Player Knowledge | Inventory | New Setup | Payoff | Exit State |
|---|---|---|---|---|---|---|---|

每个新版本必须更新。

### B. Table Read / Cold Read 思维实验

电影剧本常用 table read 暴露：

- 对话不自然；
- 信息说得太直白；
- 角色不知道为什么要说这句话；
- 节奏过慢。

在没有真实玩家时，Agent 应做一次 **simulated cold read**：

> 假设第一次看到游戏，不使用作者脑中的隐藏知识，只依据页面内容行动。

### C. Scene Objective–Obstacle–Outcome

逐场问：

1. 玩家当前目标是什么？
2. 阻碍是什么？
3. 她们能采取哪些行动？
4. 场景结束时状态发生了什么变化？

如果某个 scene 没有明确 objective 或 outcome，它可能只是“漂亮但无功能”的场景。

### D. Setup–Payoff Audit

逐项列出重要 setup，检查 payoff。

例如：

| Setup | Payoff |
|---|---|
| ★钥匙 | Library hidden passage |
| 1897 closure order | Tower blocked |
| Snake warning | Main Gate / service passage danger |
| stopped watch | Clock Room puzzle |

缺一侧就要解释。

---

## 10.5 引入游戏设计常用检查技术

### A. Branch Coverage

把所有关键选择至少走一遍。

不要求穷举所有组合，但必须覆盖：

- 每个 option
- 每个 route
- success
- failure
- timeout
- disagreement
- full agreement
- reconnect

### B. Dead-End Search

对每个状态问：

> 如果玩家现在什么都没理解，系统有没有下一步？

必须存在：

- hint
- fallback
- soft failure
- teacher recovery

至少一种。

### C. Fail-Forward Check

优先使用：

> **失败带来代价，但故事继续。**

而不是轻易 Game Over。

除非 Game Over 本身是明确设计目标。

### D. Meaningful Choice Check

每个选择问：

> 如果把这个选项删掉，玩家体验和数据是否完全不变？

如果答案是“完全不变”，它可能是假选择。

但并不要求每个 choice 产生永久分支。

局部反馈、时间代价、inventory、后续一句回忆都可以构成 meaningful consequence。

### E. Dominant Option Check

检查是否存在明显“永远最好”的选项。

如果：

> Safe + faster + more information

都集中在一个选项，那么它不能有效测量 behavior tendency。

Behavior choice 应尽量形成真实 trade-off。

### F. Information Bottleneck Check

关键剧情信息不能只存在于：

- 一个玩家；
- 一个容易错过的可选动作；
- 一句可能没读到的聊天。

关键推进信息必须有：

- redundancy
或
- fallback retrieval

### G. Pacing / Waiting Check

多人游戏中特别检查：

- 一个玩家操作时，另外两人是否长时间无事可做？
- 等待页是否明确？
- discussion 是否过长？
- puzzle 是否导致一个聪明玩家包办一切？

---

## 10.6 引入软件测试方法

### A. Happy Path

三人全部按预期行动。

检查是否正常通关。

### B. Failure Path

故意：

- 选错；
- 超时；
- 三人意见不同；
- 输入空消息；
- 重复提交。

### C. Chaos / Recovery Test

故意：

- 一人刷新页面；
- 一人断网再回来；
- Supabase 短暂失败；
- Agent API 不响应；
- Teacher 加时；
- 浏览器重复打开。

检查系统是否恢复。

### D. Configuration Check

每个版本启动时验证：

- Supabase URL
- publishable key
- table/schema
- GitHub Pages base path
- Agent endpoint

Three Doors 实验已经证明：

> 配置错误可能比游戏代码本身更早让整个系统失效。

---

## 10.7 “Red Team the Story”

每个 Agent 在版本完成后还必须故意扮演一个“不合作但合理”的玩家：

例如：

- 我不分享额外线索会怎样？
- 我一直选择最奇怪的路线会怎样？
- 三个人一直意见不同会怎样？
- 三个人完全一致，会不会反而触发错误的 disagreement 分析？
- 我不理解英文提示会不会卡死？
- 我点击得很慢会怎样？
- 我刷新网页会怎样？

目的不是防恶意攻击，而是暴露设计对“理想玩家”的隐性依赖。

---

## 10.8 Devil Check 的输出格式

每次检查必须生成一个版本审查记录：

```text
DEVIL CHECK — Version X

1. Viewpoints simulated
2. Problems found
3. Severity
   - Critical
   - Major
   - Minor
4. Root cause
5. Proposed fix
6. Fix implemented?
7. Re-test result
8. Remaining empirical questions
```

---

## 10.9 版本完成的 Definition of Done

一个版本只有同时满足以下条件才能标记为“完成”：

- 作者/Agent 已完成内容；
- Devil Check 已完成；
- Critical 问题 = 0；
- Major 问题已经修复或明确登记为 Known Issue；
- 修改后至少重新完整走一次 happy path；
- 相关 continuity/state/schema 文档已同步更新；
- CHANGELOG 已更新；
- 如果是代码版本，测试结果已记录。

也就是说：

> **“写完”不等于“完成”。**

# 11. Stage 10：形成“可开发脚本”

探索性剧本：

> 描述发生什么。

可开发脚本：

> 描述发生什么 + 系统必须做什么 + 数据必须记录什么 + Agent 怎么分析。

本项目：

V0.1 → V1.0

V1.0 中每一个重要互动应包含：

1. 玩家看到什么
2. 玩家可以做什么
3. 系统如何响应
4. 是否分支
5. 如何回流
6. 记录什么数据
7. 对应哪个 behavior pattern
8. Agent 是否介入
9. Codex 需要实现什么
10. 失败/断线怎么办

---

# 12. Stage 11：Codex 开发

不要把完整项目一次性交给 Codex。

推荐增量开发。

### Sprint 1
多人 room / state machine

### Sprint 2
private choice / reveal

### Sprint 3
DiscussionRoom

### Sprint 4
inventory / clues

### Sprint 5
Teacher Console

### Sprint 6
Agent analysis

### Sprint 7
prediction system

### Sprint 8
visual polish

每个 Sprint 都必须单独测试。

并且每个 Sprint 的交付遵循：

```text
Build
  ↓
Self-review
  ↓
Multi-viewpoint Devil Check
  ↓
Fix
  ↓
Re-test
  ↓
Accept
```

如果 Devil Check 发现 Critical 问题，该 Sprint 不得进入下一阶段。

# 13. Stage 12：三人真实测试

程序能运行 ≠ 游戏成立。

必须让真实三人玩。

观察：

- 是否知道下一步做什么
- 是否真的会讨论
- 是否出现沉默
- 哪些选项太明显
- 哪些行为题像“心理测试”
- 哪些 puzzle 卡住
- 倒计时是否合理
- 页面是否同步
- Agent 分析是否符合实际观察

# 14. Stage 13：测试分三层

## Layer 1：Technical Test

只问：
> 能不能工作？

检查：
- join
- sync
- database
- reconnect
- timer
- state transition

---

## Layer 2：Gameplay Test

问：
> 好不好玩？顺不顺？

检查：
- 节奏
- puzzle
- 分支
- 文本长度
- 等待时间
- 讨论自然度

---

## Layer 3：Educational Validity Test

问：
> 我们记录的数据真的支持 Skill 3 吗？

检查：

- 同一个 behavior pattern 是否有多场景证据
- Agent 是否过度解读
- 玩家是否认同证据
- prediction 是否真的在回答前锁定
- 学生是否理解 prediction ≠ fact

# 15. Stage 14：多轮循环

正式流程不是：

> V1 → 发布

而是：

```text
V1.0
 ↓
Test 1
 ↓
发现问题
 ↓
V1.1
 ↓
Test 2
 ↓
发现问题
 ↓
V1.2
 ↓
Test 3
 ↓
……
 ↓
Release Candidate
```

每轮只解决最重要的问题。

避免每次测试后全面重写。

但每一轮新版本形成后，都必须重新执行 Devil Check。不能因为上一版已经检查过，就假设新修改不会引入回归问题（regression）。

推荐循环：

```text
修改
 ↓
新版本
 ↓
Devil Check
 ↓
修复
 ↓
Technical / Gameplay / Educational Test
 ↓
反馈
 ↓
下一轮修改
```

# 17. Stage 15：发布前检查

发布前还必须执行一次 **Release Candidate Devil Check**。这一次不能只看新增修改，而要从头到尾完整检查整个系统，作为最后质量门。

## Devil Check
- Gitte / Anna / Linda 三视角均完整通关
- Team / Teacher / Server / Agent / Maintainer 视角均检查
- continuity matrix 已更新
- setup–payoff audit 无关键断裂
- branch coverage 覆盖主要 success / failure / timeout 路径
- reconnect / refresh / Agent failure 已做 recovery test
- Critical issue = 0

## Gameplay
- 三人能独立进入
- 没有死路
- 所有 puzzle 有 fallback
- 所有 branch 能合理回流

## Technical
- Supabase URL 正确
- GitHub Pages 正常
- reconnect 可恢复
- 重复提交受限
- timer 同步
- Teacher Console 可用

## Data
- 每条记录有 player / scene / time
- dialogue 完整
- private choice 不提前泄露
- prediction 有 locked_at

## Agent
- 输出结构化
- 有 evidence
- 有 confidence
- 不做人格式诊断
- 不因一次行为做结论

## Education
- 学生最终能解释：
  > AI 是根据行为模式做预测，不是“知道我”。

# 21. 一句话原则

> **不要一开始就试图把创意写成成品；先用最小原型不断暴露问题，再把每一个暴露的问题转化为下一轮设计输入。每完成一个新版本，都要假设它仍然有错，并从多个角色、剧情、系统和数据视角把它“玩坏一次”，修复后才进入下一轮。**

这正是《古堡逃脱》目前已经走过的研发路径。

# 22. Visual Asset Development Workflow

## 22.1 先做 Visual Asset Audit

在游戏脚本足够稳定、但正式美术尚未大量生产之前，Agent 必须逐场分类：

### A. 必须用图片
视觉本身承担空间关系、场景辨识、关键氛围、setup/payoff 或重要道具视觉记忆。

### B. 完全可以文字 / UI
只需要精确文字、选择、数字、对话、投票、状态或数据展示。

### C. 介于二者之间
不得由 Agent 单方面决定。必须提交用户讨论，明确采用“图片 / 文字 / 复用已有图片 + UI overlay”中的哪一种，然后才能进入正式 asset list。

---

## 22.2 教育型项目中的图片生产

如果 AI image generation 本身是课程学习目标，则不能把图片全部视为教师准备好的静态素材。

推荐：

```text
real game need
→ asset assignment
→ student prompt
→ AI generation
→ evaluate
→ revise
→ upload
→ review
→ use in product
```

学生因此学习：

> **Prompt → Evaluate → Revise → Deliver**

而不是无目的生成图片。

---

## 22.3 图片任务按信息复杂度分配

### Student
适合信息简单、氛围型、不承担精确空间关系、少量视觉误差不会破坏逻辑的图片。

### Teacher
适合地图、多空间关系、谜题场景、setup/payoff 高度依赖视觉一致性的图片。

---

# 23. Visual Continuity Devil Check：两阶段模式

完整 Visual Continuity Devil Check **不要求阻塞 Codex 开工**。

采用：

```text
Phase A — Pre-build Visual Freeze
            ↓
      Codex may start
            ↘
       image production
            ↓
Phase B — Full Visual Continuity Check
            ↓
Scene integration acceptance
```

---

## 23.1 Phase A：必须在开发前完成

至少确定：

- asset list
- asset keys
- picture/text/UI classification
- ownership
- basic format / aspect ratios
- Master Style Prompt
- recurring prop specification
- upload / approval data contract
- 哪些关键文字必须由 HTML/UI 表达

Phase A 完成后，核心程序开发不再等待所有图片。

---

## 23.2 Phase B：与 Codex 开发并行

每产生一批图片，就进行：

- architecture consistency
- spatial continuity
- prop continuity
- lighting continuity
- setup–payoff continuity
- UI-safe composition
- image artifact check

图片可以边开发边 review。

但：

> **任何图片在成为正式 scene asset 前必须通过 Visual Continuity Gate。**

---

# 24. Visual Continuity 的影视/游戏方法

## 24.1 Visual Bible / Style Bible

正式批量作图前必须建立：

- architectural style
- material palette
- lighting rule
- camera rule
- horror intensity
- forbidden elements
- recurring props
- character/room visual anchors

所有图片 prompt 引用同一 master style block。

---

## 24.2 Prop Continuity Sheet

重复道具必须建立：

| Prop | First appearance | Later appearance | Fixed features |
|---|---|---|---|
| Key | opening | hidden passage | material / shape / symbol |
| Watch | opening | clock puzzle | era / dial / size |
| Photograph | library | tower | tower geometry |
| Map | opening | route choice | spatial relationships |

---

## 24.3 Location Continuity Matrix

逐场记录：

| Scene | Map position | Entry direction | Exit direction | Key landmarks | Next scene |
|---|---|---|---|---|---|

---

## 24.4 Lighting Continuity

同一夜晚的图片需要建立 story-light progression。

例如：

```text
23:47 cold moonlight
→ deeper interior candlelight
→ alarm / pressure
→ midnight exterior
```

可以变化，但必须有叙事原因。

---

## 24.5 Visual Setup–Payoff Audit

任何后来必须“认出来”的东西，前面必须有可辨认的视觉 anchor。

如果两张图造型完全不同，setup/payoff 就失效。

---

# 25. Visual Asset Upload / Approval Workflow

运行时资产不应要求学生修改 GitHub repository。

推荐职责：

### GitHub
- code
- configuration
- version-controlled fallback assets

### Runtime Asset Storage
- student uploads
- teacher uploads
- versions
- approval state
- active assets

## 25.1 Asset production state

推荐：

```text
ASSIGNED
→ MISSING
→ UPLOADED

→ SUPERSEDED
```

## 25.2 游戏启动质量门

如果 required asset 尚未 APPROVED / ACTIVE：

> GAME READY: NO

不能正式开局。

---

# 26. 每个视觉版本同样必须做 Devil Check

图片不是“装饰例外”。

每完成一张关键图片、一批场景图片、一次 style 修改、一个新 map 或一次资产替换，都必须检查它是否引入新的：

- story contradiction
- prop mismatch
- spatial contradiction
- UI conflict
- misleading clue
- unwanted AI artifact

Visual QA 属于整个 Devil Check 体系的一部分，而不是美术最后的润色步骤。

---

# 27. 研发流程中的并行原则

为了减少等待：

### 可以并行
- Codex core engine
- Supabase state/data work
- DiscussionRoom
- Teacher Console
- Agent interface
- image generation
- visual review

### 不可越过的依赖

在 Scene 被标记为“完成”前：

```text
code works
+
content works
+
asset approved
+
visual continuity passed
+
scene devil check passed
```

必须同时满足。

也就是说：

> **开发可以并行，验收必须汇合。**

# 28. 更新后的版本循环

推荐每一个新版本遵循：

```text
Need / Feedback
      ↓
Design / Script change
      ↓
Technical change
      ↘
       Visual asset change（如需要）
      ↓          ↓
Devil Check   Visual Continuity Check
      ↘          ↙
        Integrated Re-test
               ↓
        Version accepted
               ↓
        Real-user test
```

任何一条支线未通过，不得把完整版本标记为 Done。
