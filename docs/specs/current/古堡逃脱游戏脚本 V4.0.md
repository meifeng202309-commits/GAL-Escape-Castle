>
> **Supersedes:** 古堡逃脱游戏脚本 V3.3.md
>
> 本版把此前 Round 1–6 已确认的剧情、多人状态、Pocket、信息来源、Visual Asset、Audio Asset 与行为分析逻辑整合为一份可交付给 Codex / Visual Agent 的统一规格。

> - **~5% Rule-Change Threshold**：除hard invariant例外，实际工作流中估计出错概率不超过约5%的假设风险，不再新增规则、阻塞生产或重开已达成一致的流程。

# 0. 文档定位

本文件在《古堡逃脱游戏脚本 V1.0》基础上重构。

V4.0 的核心目标：

1. 保持游戏表层为“古堡逃脱”，不让学生感觉自己在做行为问卷；
2. 所有正式行为选择采用“一次提交、不可修改”的原则；
3. 把“第一次个人反应”和“讨论后的群体决定”严格分开；
4. 把 Game Track 与 Behavior Track 分开；
5. Post-game / Future Agent分析如启用，顶层分析严格限制在既定六类行为模式；
6. 讨论分析中的其他指标仅作为 observable features，不扩展行为模式；
7. 为未来扩展保留接口，但 V4.0 不启用额外行为维度；
8. 明确页面、数据库、数据导出、未来Agent分析与Codex的实现要求；
9. 保持剧情设定、线索、道具与后续场景前后一致；
10. 形成可让 Codex 分阶段实现和后续维护的开发规格。

本游戏不是人格测试。所有结论只能描述：

> **“玩家在本局游戏中表现出的行为倾向。”**

不得描述为固定人格。

# 2. 六类 Behavior Patterns：唯一允许的顶层分析维度

V4.0 只分析以下六类：

1. **Planning vs spontaneity**
2. **Group role**
3. **Novelty vs familiarity**
4. **Social initiative**
5. **Handling disagreement**
6. **Reaction under pressure**

任何下列内容：

- reason giving
- evidence seeking
- stance persistence
- compromise
- voting proposal
- information integration
- help seeking
- decision facilitation
- response latency

都只能作为：

> **observable features / evidence features**

不得成为第七、第八种 behavior pattern。

# 5. 正式选择 / 投票 / Re-vote 规则

必须区分：

```text
A. Behavior First Choice
B. Group Vote
C. Game-only Step Vote
```

## 5.1 Behavior First Choice

每个behavior decision point：
1. 每名玩家只提交一次；
2. 提交后立即LOCK；
3. 不允许改写；
4. 保存原始choice与server timestamp；
5. 后续任何group vote不得覆盖它。

---

## 5.2 Group Vote / Re-vote

Group vote在**每一个vote round内**一人只能提交一次。

合法re-vote时：

> **创建新的 `vote_round`，不得覆盖旧round。**

最低身份字段：

```text
run_id
scene_id
phase_key
step_key
vote_round
player_id
decision_type
choice
locked_at
```

推荐唯一约束：

```text
run_id
+ scene_id
+ phase_key
+ step_key
+ vote_round
+ player_id
+ decision_type
```

其中：
- `step_key = null` 可用于非step场景；
- Behavior First Choice使用自己的永久LOCK identity；
- Game-only step vote与Behavior Track分离。

## 5.3 LOCK 的准确含义

`LOCK` = **同一decision identity内不可修改**。

它不意味着整个scene永远不能再投票。

合法re-vote必须：
- 由scene tie policy触发；
- 新建新的 `vote_round`；
- 不删除旧round；
- 不重新开放Behavior First Choice。

## 5.4 缺失投票

vote deadline到而不足三名玩家提交时：

```text
do not synthesize player input
do not calculate majority from only 1–2 players
phase = WAITING_FOR_MISSING_PLAYER
```

允许：
- 等待reconnect；
- Teacher `Add 30 sec`；
- Teacher使用合法 `SKIP CURRENT INTERACTION` / `RESOLVE & CONTINUE`。

若Teacher Override导致未取得某玩家投票：

```text
choice = null
validity = invalid_teacher_override
```

技术故障导致缺失：

```text
choice = null
validity = missing_technical
```

当前path按设计不要求该字段：

```text
choice = null
validity = not_applicable
```

**不得替玩家投票。**

## 5.5 ACT 1–5 Teacher Override Safe-Resolution Allowlist — Sprint 3C HARD RULE

本节定义 Sprint 3C 最小 Teacher deblock / override 在 ACT 1–5 中唯一允许的 scene-owned 映射。

总原则：

- Teacher client只提交 `SKIP_CURRENT_INTERACTION` 或 `RESOLVE_AND_CONTINUE`；
- client不得提交destination、player identity、choice、answer或branch result；
- server必须按当前 `scene_id + phase_key` 从本allowlist选择结果；
- 不在allowlist中的scene/action组合必须拒绝，且不得修改state或写入override event；
- override永远不伪造player choice / vote / message / response time / acknowledgement；
- override之前已经真实产生的数据全部保留；
- 只有因override而没有真实产生的behavior字段保持 `null`，并标记 `invalid_teacher_override`；
- Game Track-only状态可由server推进，但必须记录独立 `teacher_override` event，`behavior_scoring=false`；
- GAL端不显示“Teacher Override”字样，只看到正常canonical剧情 / UI文本；
- 本节所有会推进Game Track的override，后续真实behavior event均带
  `context_provenance.upstream_teacher_override = true`，
  但这些后续真实behavior本身仍为valid；
- Sprint 3C仅覆盖ACT 1–5；ACT 6+一律不在本allowlist内。

# 7. Castle Lore：统一世界设定

为防止恐怖元素互相矛盾，V4.0 采用以下固定世界规则。

### 1897 官方事件

1897 年，当地政府发布封闭通知：

> 西塔与地下服务通道因结构损坏和毒蛇出没而封闭。

### 古堡内部传闻

旧仆人日记记录：

> 接近午夜时，古堡旧暖气通道变暖，蛇会从地下和墙体通道进入较温暖的大厅。

### 空间规则

- Library 虽不位于几何中心，但有明确通路连接不同区域，是地图上已知的公共会合点；
- Great Hall 在 night bell 后，部分外侧公共入口会由内侧铁门封闭；后续仍可通过内部路线 / servants' passage 抵达；
- Main Gate 从内部无法直接开启；
- West Tower 自 1897 年起正式封闭；
- 部分旧服务通道仍存在；
- Clock Room 与 1897 事件有关。
- 公共走廊仍残留少量旧黄铜方向牌，可指向 Library / Great Hall / Main Gate / West Tower / Chapel 等主要公共区域；方向牌不显示完整地图、距离、封闭状态或安全信息，因此不能替代 Gitte 的 Castle Map。

### 超自然元素

- 会说话的画像；
- 部分钟表异常；
- 手机之间出现无法解释的 local network。

这些现象可以保持神秘，不要求在游戏中完全解释。

### 一致性规则

游戏后续不得突然新增：

- 未铺垫的新怪物；
- 与 1897 完全无关的新灾害；
- 推翻前面世界规则的文字提示。

# 9. ACT 1：WAKE UP

## 9.0 ACT 1 通用执行规则（Codex）

ACT 1 的三个角色场景统一采用：

```text
Scene enter
→ Opening text
→ Room image
→ Automatic visible information
→ Private First Action
→ LOCK
→ Local consequence
→ ACT 1 complete
→ 等待另外两名玩家完成 ACT 1
```

### 9.0.1 First Action 与关键物品分离

ACT 1 的 first action 只回答：

> **“你醒来后首先做什么？”**

它用于 Behavior Track，不得决定后续剧情必需物品是否永久丢失。

规则：

- first action 每人只能提交一次；
- 提交后立即 LOCK；
- first action 可以让玩家**更早发现额外/隐藏信息**；
- progression-critical objects 不依赖 first action 是否选中；
- progression-critical objects 将在 ACT 2 的 Mandatory GRAB checkpoint 被强制收入个人 Pocket；
- optional / hidden clues 不因 GRAB 自动解锁。

### 9.0.2 Pocket 原则

Pocket 只装入**可携带 object**。

object 内部的信息只有在玩家重新打开 / 检查该物品时展示。

因此：

> `GRAB object ≠ automatically read all information inside the object`

每个 Pocket item 至少定义：

```text
item_key
display_name
asset_key / asset_keys
default_view
available_actions
exact_UI_text
hidden_or_optional_information
```

精确数字、符号、文字仍由 HTML / UI 同步显示；AI 图片只负责物件外观与视觉识别。

### 9.0.3 Pocket inspect asset 命名原则

建议：

```text
prop_[role]_[item]_[view]
```

例如：

```text
prop_gitte_number_note_front
prop_gitte_number_note_back
prop_linda_watch_face
prop_linda_watch_back
```

Codex 依据 `asset_key` 播放相应图片。

GPT-生图 Agent 依据“Visual content”制作图片。

### 9.0.4 屏幕信息标准化显示模式

Codex 统一支持三种 UI message mode。**从本节开始，每一处明确的“屏幕显示 / UI显示 / broadcast”都必须同时写明 display mode。**

#### A. `CINEMATIC_MESSAGE`  
用于梦境低语、撞击声、短暂异常提示、氛围文字。
- minimum display：3 秒；
- 3 秒后 `[CONTINUE]` 可用；
- 玩家不操作时，8–10 秒自动淡出。

#### B. `CRITICAL_INFO`
用于 Story Time、government notice、谜题关键文字、必须准确读取的信息。
- 不自动消失；
- 玩家必须点击 `[CONTINUE]` / `[CLOSE]`；
- 精确文字必须由 HTML / UI 显示。

#### C. `ACTION_SCREEN`
用于 Private Choice、`[GRAB]`、`[FLIP]`、`[SHARE PHOTO]`、Final Vote。
- 不自动消失；
- 直到玩家完成当前操作。

除非 scene 明确另有规定，后续所有屏幕信息均使用上述标准模式。

### 9.0.5 Student Text / Localization Contract — 强制

所有真正显示给GAL的runtime文字，默认：

```text
English = master source only
Dutch = displayed
Chinese = displayed
```

标准显示顺序：

```text
Nederlands
中文
```

English master用于：
- 文案定稿；
- 翻译基准；
- Codex content key；
- review / maintenance。

**English不得作为普通GAL runtime第三种显示语言。**

语言无关元素可只显示一次，例如：
- player name；
- `23:49`；
- `41739`；
- `★`；
- A/B/C station ID。

Text catalog至少区分：

```text
text_type = static | template | internal | future_analysis
display_policy = bilingual | nl_only_artifact | hidden
```

### Canonical Localization Catalog — HARD SOURCE OF TRUTH

经Teacher review确认的当前runtime translation catalog：

```text
docs/specs/current/localization/GAL_Castle_Escape_Text_Catalog_V1.0.csv
```

该CSV是 **English master → Nederlands → 中文** 的唯一canonical translation source。

规则：
- V4.0继续定义剧情、语义、scene usage、显示规则与特殊排版；
- CSV保存已批准的runtime翻译；
- CD不得自行重新翻译、机器翻译或另建第二套独立translation table；
- GAL-facing runtime text必须通过 `text_key` 解析catalog；
- English只作为master / review source，普通GAL runtime不显示；
- `nl_only_artifact` 保留中文列仅用于Teacher review，runtime仍只显示荷兰语；
- template必须保留runtime变量，不得把示例值写死；
- 修改English master时，如果语义改变，对应catalog行必须重新review后才可用于runtime。

规则：
- `static`：固定GAL-facing文本；
- `template`：玩家名 / 地点 / 数值等由runtime变量填充；
- `internal`：规格说明、示例、developer note，不可进入GAL UI；
- `future_analysis`：Post-game/Future Analysis使用，不属于当前游戏GAL UI。

#### 唯一明确语言例外：1897 Municipal Closure Order

该道具是1897年本地政府原始文件，因此：

```text
display_policy = nl_only_artifact
```

文件本体/inspect UI只显示荷兰语，不显示中文；English仍作为master source保存在content catalog中。

#### ACT 14 Ending Typography — 不可自动改写

English master：

> **But the castle remembered everything you did.**  
> **THEY know who you are.**

规则写死：
- 两句**整句加粗**；
- 不得把整句转成ALL CAPS；
- 只有第二句中的 `THEY` 保持全大写；
- 禁止CSS `text-transform: uppercase` 作用于这两句；
- 荷兰语对应行同样只强调代词：`**ZIJ weten wie jullie zijn.**`，不得把整句全大写；
- 中文没有大小写概念，整句加粗即可；
- localization renderer不得擅自把第二句改成 `THEY KNOW WHO YOU ARE.`。

- Final Vote 仍只有 A–E 五个地点。

- `I'm scared` 是场景台词；
- 不得直接解释为胆小、依赖或任何固定人格；
- 可记录为 observable：`requested_direction = true`，但只作为 contextual evidence。

## 10.6 为什么 Library 是最终推荐地点（设计层）

玩家需要在五个有效选项中比较风险与可达性。

如果相关玩家主动分享自己掌握的信息，团队可能获得：

- **Library**
  - Gitte 的地图显示有明确通路连接不同区域；
  - 暂无已知封闭或危险信息。

- **Great Hall**
  - Anna 知道 night bell 后 Great Hall 的外侧公共入口会从内部封闭。

- **West Tower**
  - Linda 知道 1897 government closure；
  - 深入阅读后可能还知道 structural damage / venomous snakes。

- **Main Gate**
  - 地图上目标明确；
  - 但没有足够信息证明三人能在那里安全会合或直接离开。

- **Chapel**
  - 地图上醒目、看似适合集合；
  - 但 Gitte 私下听见过：
    > **“礼拜堂里的蛇王……很生气。”**

因此 Chapel / Great Hall / West Tower 都能成为真实 discussion material。

Library 应是：

> **在充分交换已有信息后，已知风险最低、最容易共同接受的 meeting point。**

不是因为系统直接告诉她们答案。

## 10.7 Final Meeting Vote

A. Library  
B. Great Hall  
C. Main Gate  
D. West Tower  
E. Chapel

final vote：

- 单独保存；
- 不覆盖 first meeting choice；
- 用于判断 `changed_position`。

### Authoritative Route Update

Final Meeting Vote / fallback 一旦产生最终地点，服务器必须执行：

```text
first_meeting_choice = keep locked as Behavior evidence
final_meeting_result = resolved group location
current_route_target = final_meeting_result
```

三名 GAL 同时看到：

`display_mode = CRITICAL_INFO`

> **MEETING POINT UPDATED: [LOCATION]**  
> **Change course now.**

F 选择者与 A–E 选择者从此使用同一个 `current_route_target`。

> 设计说明：Private First Meeting Choice 记录“最初想去哪”；Final Vote 决定 Game Track 中现在真正往哪里走，避免玩家仍沿旧路线移动。

### 结果规则

本scene显式配置：

```text
tie_policy = SINGLE_REVOTE_THEN_FALLBACK
revote_window_sec = 30
max_revotes = 1
fallback_resolution = library
```

3:0：

> consensus

2:1：

> majority decision

1:1:1：

> **No consensus. One final 30-second discussion.**

追加讨论必须新建 `discussion_session_id` 与 `vote_round = 2`。

若仍 1:1:1：

系统 fallback：

> **UNKNOWN SENDER:**  
> **Three girls. Three answers. How disappointing.**  
> **Go to the Library. Try not to die on the way.**

该 fallback：

- 只防止游戏卡死；
- 不参与 behavior scoring；
- 不改写任何人的 first choice / final vote evidence。

## 10.8 Failed Rendezvous Rule

如果 group final decision 不是 Library：

> **blocking event 必须发生在三条个人路线真正汇合之前。**

因此：

- 三人不会先在错误地点实际碰面；
- local consequence 发生后仍处于分散状态；
- 然后 fold back 到 Library。

这样保持：

> **Branch → Local Consequence → Fold Back**

任何failed rendezvous完成local consequence并回Library时，服务器必须：

```text
final_meeting_result = keep original resolved meeting result
current_route_target = library
wayfinding_target = library
```

`final_meeting_result` 保留历史投票；  
`current_route_target` 表示当前真正执行路线，避免reconnect / Teacher Console显示旧目标。

### 12.4.1 Server-authoritative post-90-second fallback — HARD RULE

Library Box puzzle启动时服务器保存：

```text
puzzle_started_at
puzzle_deadline = puzzle_started_at + 90 sec
hint_stage
resolved_at
```

正确code仍为：

```text
4 – 1 – 7 – 3 – 9
```

如果在任一fallback step之前玩家已经正确解开：
- 立即停止所有后续fallback；
- 不再自动锁定新的转轮；
- 正常进入12.5。

如果现实时间90秒仍未完成，系统进入**Game Track-only**渐进fallback。  
所有自动动作均由服务器拥有，不计player attempt，不生成player choice，不进入behavior scoring。

固定顺序如下：

| 从 `puzzle_started_at` 起 | Server action | GAL-facing text_key |
|---|---|---|
| 90 sec | 左起第1个转轮自动设为 `4` 并锁定 | `act03.014` |
| 105 sec | 左起第2个转轮自动设为 `1` 并锁定 | `act03.017` |
| 120 sec | 左起第3个转轮自动设为 `7` 并锁定 | `act03.018` |
| 135 sec | 左起第4个转轮自动设为 `3` 并锁定 | `act03.019` |
| 150 sec | 左起第5个转轮自动设为 `9` 并锁定；box自动resolve/open | `act03.020` → `act03.015` |

对应English master：

> **One of the five wheels clicks into place.**

> **A second wheel clicks into place.**

> **A third wheel clicks into place.**

> **A fourth wheel clicks into place.**

> **The final wheel turns and clicks into place.**

最终继续使用既有：

> **The lock releases with a dry click.**

实现规则：

- 每个自动锁定的digit成为server-owned fixed wheel；玩家只能操作尚未锁定的wheel；
- timeout progression只推进 `hint_stage`，**不得增加 `attempt_number`**；
- 每个stage只允许写入一次system event，建议：
  `event_type = puzzle_fallback_hint`，
  `resolution_source = system_fallback`；
- 每次自动提示记录：
  `escape_penalty_event = puzzle_hint_used`；
- reconnect后按server time + persisted `hint_stage`恢复；
- 如果客户端在多个deadline之后才重新连接，服务器必须按顺序、幂等地补齐已经到期的stage，不能重复写历史event；
- 并发client不得造成同一wheel重复锁定、重复open或重复创建group item；
- 第5个wheel自动锁定后直接server-resolve box，**不要求伪造一次玩家提交**；
- 整个fallback只改变Game Track，不产生任何“更聪明 / 更慢 / 更依赖提示”的behavior结论。

### 50.7.1 Source-of-truth separation

### 50.7.2 asset_key is opaque — HARD RULE

所有Agent：

- never invent an \`asset_key\`
- never translate it
- never abbreviate it
- never normalize dot / underscore / hyphen
- never reconstruct it from a filename
- never substitute a \`MASTER-XX\` ID unless registry explicitly maps it

Human wording只能通过：

\`\`\`text
exact display_name / explicit alias
→ exact canonical asset_key
\`\`\`

如果没有exact mapping：

\`\`\`text
STOP
ASSET KEY NOT FOUND
\`\`\`

不得猜。

---

### 50.7.3 Version semantics

必须分开：

\`\`\`text
latest_version
active_version
\`\`\`

定义：

- \`latest_version\` = 已存在的最新candidate version number
- \`active_version\` = runtime当前唯一使用version
- next candidate = \`latest_version + 1\`
- runtime lookup = \`active_version\`

\`APPROVED\` 与 \`ACTIVE\` 不同：

- APPROVED = eligible for promotion
- ACTIVE = runtime当前唯一版本

允许多个APPROVED。

每个 \`asset_key\` 最多一个ACTIVE。

### 50.7.4 VA production transaction

对每一个**production candidate**，VA必须：

\`\`\`text
1. exact-path fresh read assets/asset-registry.json
2. resolve exact display_name / alias
3. obtain exact asset_key
4. read latest_version
5. calculate next candidate version
6. read Castle Visual + continuity references
7. generate image
8. post-process to canonical filename
9. create matched JSON sidecar
10. calculate width / height / SHA-256
11. re-fetch registry immediately before commit
12. if version state changed, recalculate candidate version and rename pair
13. upload image + JSON to GitHub staging
14. re-read GitHub
15. verify path / blob / non-zero size / SHA-256
16. leave candidate PENDING_REVIEW
17. Teacher reviews
\`\`\`

Canonical candidate filename：

\`\`\`text
{asset_key}__vNNN.webp
{asset_key}__vNNN.json
\`\`\`

Recommended staging path：

\`\`\`text
assets/staging/{asset_key}/vNNN/
\`\`\`

Production assets **不得**放入：

\`\`\`text
agent-comms/
\`\`\`

## 50.9 ~5% Rule-Change Threshold — USER DIRECTIVE

这是从V4.0起所有Agent的效率治理规则。

### Default

如果某个新提出的failure mode，在**当前真实项目工作流**中经合理工程判断的发生概率：

\`\`\`text
<= approximately 5%
\`\`\`

则默认：

- 不新增规则；
- 不增加production step；
- 不阻塞当前工作；
- 不为它重构已达成一致的流程；
- 必要时只记录为non-blocking note。

只有当风险大约：

\`\`\`text
> 5%
\`\`\`

时，才默认值得提出新的workflow rule / redesign。

这里的5%是：

> **engineering heuristic, not a statistically measured confidence threshold.**

Agent不得为了证明“理论上可能”而不断增加规则。

### Hard-invariant exception

即使概率低于约5%，如果后果会直接违反已锁定hard invariant，可以升级处理，例如：

- credential / secret exposure
- destructive loss of canonical asset / student data
- silent corruption of asset identity / runtime identity
- overwrite of immutable history
- silent security bypass

此例外应保持狭窄，不得把一般质量偏好包装成hard invariant。

### Current asset-workflow application

当前production是单一、顺序式visual workflow。

因此：

> **现在不增加atomic version reservation / CAS机制。**

当前足够：

\`\`\`text
fresh registry read
→ latest_version + 1
→ pre-commit registry re-read
→ immutable staging
→ post-upload verification
\`\`\`

只有当实际出现多个并发asset writer，使version collision的实践风险上升到约 >5% 时，再引入reservation / compare-and-swap。
