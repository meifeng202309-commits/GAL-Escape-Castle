- current HEAD vs the relevant failed/frozen baseline;

## 4. Recurrence thresholds

GA recommends different thresholds for efficiency/process issues versus authority/safety issues.

### A. Allocation / parallel-efficiency pattern

Formal cooperation-rule revision becomes justified if, after this transition cycle, either:

1. the same non-duplicative allocation failure occurs in **2 of the next 3 genuine CD/ISA cycles**; or
2. one recurrence causes a material loss of parallelism large enough to waste a substantial bounded Work Package; or
3. CA repeatedly becomes a serialization chokepoint because plan/interface review is being invoked for work that should remain Class A / standing-envelope work.

At that point the issue should be promoted from:

`OBSERVATION / TRANSITION`

to:

`SYSTEMIC PROCESS ISSUE`

and a minimal rule amendment may be appropriate.

### B. CD Action Log compliance

After CD completes the current reconciliation:
- one later omission should be treated as a repeated compliance issue and explicitly called out;
- if the omission pattern happens **again after that reminder**, then stronger monitoring/gating should be considered.

The first response should still use the existing V1.1 rule rather than invent a new rule.

### C. Authority / safety boundary

Do **not** wait for recurrence when the issue involves:
- split mutation authority;
- migration collision;
- protected canonical-source modification;
- two active writers on the same authority surface;
- security/auth boundary;
- persistence/lifecycle semantics;
- false PASS/release authority;
- player-behavior or provenance corruption.

A single credible occurrence in those categories is enough for immediate escalation because the downside is not merely coordination inefficiency.

## 5. Risk of “observe first”

GA does **not** see a serious safety gap in observing the current two issues before changing rules.

The current observations are:
- allocation timing / labor-saving efficiency;
- Action Log compliance.

Neither currently shows:
- authority split;
- migration collision;
- canonical bypass;
- unsafe runtime semantics;
- audit independence failure.

Existing rules already cover the actual safety boundaries.

Therefore adding new mandatory process now would likely create more coordination cost than risk reduction.

## 6. Operational stance for the next cycles

Keep Cooperation Rules V1.0 unchanged.

CA should:
- continue current operational vigilance;
- enforce COOP-001 under V1.1;
- collect evidence from several steady-state CD/ISA cycles;
- distinguish efficiency observations from authority/safety violations;
- escalate only when the recurrence thresholds above are met.

This disposition supersedes the *proposed mandatory-rule-change implication* of the 10:09 self-review, but does not erase its factual record.
